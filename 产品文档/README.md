# OTD 订单交付平台 · 产品文档

> 版本 v1.0 · 2026-11-15

OTD（Order to Delivery）订单交付平台，面向针织 / 袜业代工企业：把「客户企划 → 打样 → 测试 → 报价 → 开发移交 → PO 复核 → 辅料与包装 → 备料与生产 → 验货与放行 → 出货与结算」10 个环节串成一条主线，让每一单的进度、责任和异常都看得见；并提供 AI 助手、客户流程配置、业务自动巡检、多角色看板、主数据适配器、RBAC 权限 6 项平台能力。

本项目以一段第三方产品演示视频（健盛集团 OTD 平台，v2.3.0）为参照做**通用版**：行业模型照搬针织 / 袜业，但品牌、吉祥物、客户名单、基地名一律只作样例。本目录是全部需求、设计和技术文档，也是 AI 开发时的事实来源。

### B. 主线 10 节点

| 编号 | 节点 | 闸门 | 对应模块 | 主要单据 |
| --- | --- | --- | --- | --- |
| N01 | 企划接入 | | M02 | 企划 |
| N02 | 打样与批复 | | M03、M05 | 打样单、寄样单 |
| N03 | 测试 | | M06 | 送测单、测试报告 |
| N04 | 报价 | | M04 | 报价单 |
| N05 | 开发移交 | ◆ G1 | M15 | 开发移交包 |
| N06 | PO 复核 | | M09 | 客户订单 |
| N07 | 辅料与包装 | | M07、M13 | 包装方案、采购单 |
| N08 | 备料与生产 | | M08、M09、M13 | 生产进度登记 |
| N09 | 验货与放行 | ◆ G2 | M10 | 验货单 |
| N10 | 出货与结算 | | M11、M12 | 订舱单、出货单、应收单 |

- 节点状态：**待启动 / 进行中 / 已完成 / 受阻 / 不适用**（「不适用」= 该客户的流程配置没启用这个节点对应的服务模块；「受阻」= 闸门条件不满足或存在红灯巡检命中）。视频可见前三个，后两个为推断。
- **G1 开发移交「五项齐套」**（视频可见）：样品已批准 + 报价已被客户接受 + 测试报告有效 + QRS 品质参考样已留存 + 技术资料包已上传；移交后开发资料冻结，改动走变更。
- **G2 验货放行「三条件」**（视频说「三条件缺一不放行」，具体条件为推断）：① 终验（FRI / FINAL / FQC）结论合格；② 该款适用的测试报告全部在有效期内且合格；③ 包装方案客户已确认且装箱单齐套。

### D. 单据状态（规范名）

| 单据 | 状态流 | 视频情况 |
| --- | --- | --- |
| 企划 | 识别中 → 提取完成 → 已确认 → 已归档（另有：识别失败） | 前三个可见 |
| 打样轮次 | 已下达 → 待接收 → 原料采购 → 上机打样 → 质检 → 待取样 → 已寄样 → 待批复 → 已批准 / 需改样 | 「已下达」见巡检，5 个阶段可见，批复类推断 |
| 送测单 | 草稿 → 待送样 → 测试中 → 测试完成；结论（合格 / 不合格）为附加字段 | 视频可见（测试记录列表）；进度 4 步：寄样并申请 → 机构检测 → 出具报告 → 结果登记 |
| 测试报告 | 有效 → 即将过期（30 天内）→ 已过期 | 有效期可见，状态推断 |
| 报价单（每轮） | 草稿 → 成本审核中 → 已报价 → 已接受 / 已拒绝 / 已失效 | 「成本审核中」「已报价」可见 |
| 开发移交包 | 齐套中 → 已移交（冻结） | 推断 |
| 客户订单 | 待确认 → 待排产 → 生产中 → 待发货 → 已完成；另有：已取消（已有出货的订单不可取消） | 视频可见（订单状态分布 + 第 1 / 5 阶段） |
| 包装方案 | 草稿 → 待客户确认 → 已确认；改已确认的方案生成新版本 | 「已确认」「v3」可见 |
| 采购单 | 已下单 → 部分到货 → 已到货；另有：已取消 | 推断 |
| 验货单 | 待排期 → 已排期 → 已验（合格 / 不合格）→ 整改复验 → 已放行；另有：已取消 | 「已验」「整改复验」「登记放行」「取消验货」可见 |
| 订舱 / 出货 | 订舱确认 → 装箱完成 → 已开船 → 已到港 → 已签收 | 视频可见 |
| 应收单 | 未到期 → 待收款 → 部分收款 → 已收款；负数单据为「待冲抵 → 已冲抵」；逾期、争议挂起是附加标记 | 「未到期 / 待收款 / 部分收款 / 待冲抵」可见 |
| 巡检命中 | 红灯 / 黄灯 / 绿灯；严重度 高 / 中 / 低；处理：待处理 → 处理中 → 已关闭 | 灯与严重度可见 |
| 同步执行 | 成功 / 部分成功 / 失败；记录级：成功 / 失败 / 跳过 / 重试中 | 视频可见 |

权限三维：**菜单（功能点）× 组织（数据范围）× 客户（客户范围）**，三者取交集。

数据范围四档：**仅本人 / 本组织 / 本组织及下级 / 全部数据**。视频里只出现了「仅本人」「本组织及下级」「全部数据」三档，「本组织」为推断补充（给技术、品质、采购等职能部门用）。

## 关键决策一览

| 方面 | 决策 | 出处 |
| --- | --- | --- |
| 定位 | 参照视频做通用版，行业按针织 / 袜业建模；品牌、客户、基地只作样例 | 本文 |
| 部署形态 | 单企业私有化部署（一套系统服务一个集团，多事业部、多基地），不做多租户 SaaS | 需求 2 |
| 主线 | 10 节点 + 2 个闸门；节点是否启用由客户流程配置决定 | 业务设计 2、4 |
| 前端 | 沿用 `~/WebstormProjects/frontend-react-template`：Vite 8 + React 19 + TypeScript + shadcn/ui + Tailwind CSS 4 + React Router 8（Data Mode）+ TanStack Query 5 | 技术方案 1、13 |
| 后端 | NestJS 12 + PostgreSQL + Redis + BullMQ，TypeScript 全栈 pnpm monorepo；接口与后台任务是同一个工程（`apps/api`）的两个启动入口 | 技术方案 1、3 |
| ORM | Drizzle：数据范围条件能注入到联表和报表 SQL，与 LuckDay 一致 | 技术方案 1 |
| AI | Claude（`claude-opus-5-5`），助手只能读当前用户有权限的数据，回答必须带数据来源和截止时间；主线不依赖 AI，AI 不可用时可手工走通 | 业务设计 8、技术方案 9 |
| AI 接入路径 | 待定：Claude API 直连 / Amazon Bedrock / Google Vertex AI，按企业所在地区与数据出境合规决定 | 技术方案 9、20 |
| 语言 | 首发简体中文 + English，预留越南语；业务数据不翻译 | 需求 4 |
| 主题 | 7 套主题（品牌红 / 科技蓝 / 松柏绿 / 琥珀金 / 藏青蓝 / 极简白 / 暗夜黑）+ 自定义主色 | 界面设计 2 |
| 助手形象 | 名称、头像、吉祥物可配置，默认「OTD 助手」，不使用视频里的吉祥物 | 界面设计 6 |

## 暂缓决定的事项

- 服务器与托管：私有机房还是云；是否需要等保。
- 内部 ERP 对端的具体系统与接口方式（视频里是环思），需要拿到对方接口文档后才能定字段映射。
- 客户系统对接清单（哪些客户有系统要对接、用 API 还是文件）。
- 登录方式是否接入企业微信 / 钉钉 / 飞书 / OIDC 单点登录。
- AI 接入路径（Claude API 直连 / Amazon Bedrock / Google Vertex AI）与是否申请零数据保留。
- 内部报价公式：视频样例 #12593 的内部报价 19.31 = 成本 16.09 × 1.20（内部报价页签显示策略 PS-001、「加成毛利 16.7%」），用头部 PS-002 的「目标利润率 18%」推不出来；倾向「按策略的成本加成率」，需业务方确认（业务设计 12）。
- G2 放行三条件的具体内容（视频只说「三条件缺一不放行」），需业务方确认。
- 生产排程是否做到机台级（一期只做进度登记，不做 MES）。
- 远端代码仓库。

## 维护规则

1. 需求变化先改需求文档，再同步改业务设计、界面设计、技术方案里受影响的部分；原型随界面设计更新。
2. 本 README 的「全局统一约定」是唯一口径：新增模块、单号、状态、角色先在这里登记，再在其他文档引用。
3. 每份文档顶部的版本号随修改递增；删除的需求不直接抹掉，标记为后续版本或已废弃并写明原因。
4. 「视频可见 / 推断」标记要保留：推断项被业务方确认后改为「已确认」，并注明确认人和日期。
5. 代码放在 `OTD-Platform` 目录（本目录的上一级），本目录随代码一起纳入版本管理；改功能时代码和文档在同一个提交里一起改。
6. `视频素材/` 里是第三方演示视频的截图和字幕，含其品牌、客户名和人员姓名 / 邮箱 / 手机号。建远端仓库前先决定是否把它排除在版本管理之外（`.gitignore`）或只在内部保存。
